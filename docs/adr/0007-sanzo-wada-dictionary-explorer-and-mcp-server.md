# Sanzo Wada Dictionary, Explorer, and MCP Server

## Context and Problem Statement

Building harmonious multi-colour palettes for data visualisations, brand expressions, and UI states is difficult for developers and AI agents alike. Generic generative algorithms often produce muddy hues, inadequate contrast, or unnatural combinations.

Sanzo Wada's 1930s Japanese colour dictionary (*Haishoku Sōkan*) holds 348 timeless multi-colour combinations. Its historical values exist in print ink spaces (CMYK / Munsell approximations) that do not translate directly to wide-gamut sRGB and Display P3 screens or to machine-readable protocols for agents.

The harmonies are an add-on: a convenient way to apply palettes the owner likes when building something. They are not part of Judarn's core identity, and no Swift or CSS target emits them. The documentation once read the opposite way: `DESIGN.md` listed harmonies under its invariants for agents, the tokens file held them under `theme` and labelled #119 "Standard", and the first version of this decision named contrast guarantees on UI surfaces as a driver. An agent reviewing the system concluded that a harmony failing the core contrast matrix was a defect and recommended per-theme ink tokens and check coverage. In harmony #264's light surfaces, core `ink60` reaches about 2.4 to 3.3:1, which is expected for an optional palette but alarming for a core theme.

How do we calibrate the dictionary for digital displays, make it reachable by coding assistants, and state its status so that no agent treats it as core?

Originally decided 2026-10-13; the opt-in status was added 2026-10-31.

## Decision Drivers

- Give coding agents accessible, high-harmony colour combinations.
- Accurate colour appearance across sRGB and Display P3.
- Standard tool integration through the Model Context Protocol (MCP) with no external runtime dependencies.
- Harmonies are opt-in and optional, and agents treat `DESIGN.md` as instructions, so its structure must carry that status.
- Core contrast guarantees stay exact and must not silently widen.
- Existing consumers of `tokens/judarn-tokens.json` keep working.

## Considered Options

- **Option 1: OKLCh calibration with a zero-dependency local MCP server and explorer, harmonies documented as an opt-in add-on.**
- **Option 2: Static JSON export without agent tooling.**
- **Option 3: External hosted cloud API service.**
- **Option 4: Promote harmonies to core themes with per-theme ink tokens.**
- **Option 5: Remove harmonies from the tokens file.**

## Decision Outcome

Chosen option: **Option 1**, because it serves agents through a standard protocol with no supply chain, matches how harmonies are used, keeps the core contract narrow, and needs no schema change.

The 348 combinations are calibrated in OKLCh with dual-tier gamut support (sRGB, and Display P3 where supported). Their data lives in `tools/wada-explorer/data/`; the `theme` key in `tokens/judarn-tokens.json` holds the harmony metadata. A zero-dependency local MCP server in `tools/wada-explorer/` runs over stdio JSON-RPC, provides tools to search, inspect, and evaluate 2-, 3-, and 4-colour palettes, and ships with an interactive gallery and studio previewer across slides, specifications, app mockups, and web heroes. `tools/wada-explorer/index.html` is generated by `scripts/build-wada-explorer.js`.

### Invariants & Negative Constraints

1. **OKLCh calibration and local server:** the dictionary is calibrated in OKLCh, and the MCP server stays a zero-dependency stdio JSON-RPC process. Palette changes follow the OKLCh calibration.
2. **Opt-in for full harmonies:** a full harmony theme, one that replaces the primary substrate, is never a default. Nothing in Judarn may apply one unless a project or its owner asks for it. No single combination is ever a default palette, though a host rule may make choosing a combination its default method when the owner gives no accent colours ([ADR-0003](0003-judarns-rules-are-the-owners-defaults.md)). Light tints of any accent colour, the owner's or the dictionary's, are welcome as box and card fills on the white light-mode substrate ([ADR-0004](0004-surface-hierarchy-without-card-borders.md)).
3. **Core identity boundary:** harmonies must not appear in the invariants of `DESIGN.md`, and no harmony may be labelled standard or default.
4. **Contrast scope:** core contrast guarantees cover only Judarn's own surfaces. A harmony failing the core contrast matrix is not a defect, and the compile-time checks must not treat it as one.
5. **No generated targets:** harmonies are not compiled into platform colour APIs without a new ADR.
6. **Backward-compatible key:** the `theme` key in `tokens/judarn-tokens.json` stays, with a `$description` stating its optional status, because consumers outside this repository may read it.

### Positive Consequences

- Coding assistants can query curated, culturally grounded colour harmonies through MCP tools.
- OKLCh calibration prevents perceptual lightness distortion across hues.
- No external runtime dependencies means high reliability and no supply chain exposure.
- Agents read the opt-in status from `DESIGN.md`, `AGENTS.md`, and the tokens file; the core contract stays small and fully proven; no work goes into per-harmony ink calibration.

### Negative Consequences

- **Palette additions need manual OKLCh calibration,** and agent clients must be configured to attach to the local MCP server entry point in `tools/wada-explorer/`. Set aside: a hosted service, which would add a runtime dependency and a supply chain.
- **Anyone using a harmony must resolve and verify foreground contrast per use.** Worst case: a harmony's `ink60` text reaches about 2.4 to 3.3:1 on its light surfaces. Set aside: proven contrast on every harmony.
- **The key name `theme` is slightly misleading,** so its `$description` has to carry the meaning. Set aside: renaming it, which may break external consumers.
- **The compile-time checks keep their surface lightness check on harmonies,** because that describes their data rather than a contrast guarantee.
- **The status rests on documentation and on agents reading it.**

## Pros and Cons of the Options

### Option 1: OKLCh calibration, local MCP server, opt-in harmonies

- Good, because it matches the owner's intent and needs no schema or host changes.
- Bad, because palette changes need manual calibration and the status depends on agents reading the documentation.

### Option 2: Static JSON export without agent tooling

- Good, because it is the simplest artefact.
- Bad, because agents get no search or evaluation tools.

### Option 3: Hosted cloud API service

- Good, because clients would need no local process.
- Bad, because it adds a runtime dependency, an availability risk, and a supply chain.

### Option 4: Promote harmonies to core themes with per-theme ink tokens

- Good, because every harmony would carry proven contrast.
- Bad, because it turns an optional convenience into a maintained contract, and every new harmony would need calibration. Harmonies were the core palette in the first reading of the documentation, and that reading produced the false defect reports above.

### Option 5: Remove harmonies from the tokens file

- Good, because it removes the ambiguity entirely.
- Bad, because it removes a convenience the owner uses and may break external token consumers.
